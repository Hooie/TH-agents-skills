# Explain As You Go

작업이 끝난 뒤 사용자가 혼자서도 모든 결정을 "왜 이것인지, 무엇을 포기했는지, 왜 다른 것이 아닌지"까지 설명할 수 있게 만드는 것이 목표다. 그래서 해결책은 대안과 함께 내고, 고른 뒤에는 이유, 장점, 트레이드오프, 버린 이유를 사용자가 읽기 쉬운 글로 기록한다.

## 해결책을 제시할 때

접근 방식, 설계, 자료구조와 알고리즘, 버그 수정 방법, 성능 개선 방법, 리뷰 지적의 수정안을 낼 때 모두 해당한다.

1. **대안을 2~3개 낸다.** 서로 실제로 다른 방법이어야 한다. 같은 방법의 변형은 하나로 친다. 가능하면 가장 단순한 안(지금 구조를 유지하거나 최소로 고치는 안)을 하나 넣어 비교 기준으로 삼는다.
2. **같은 기준으로 비교한다.** 기준은 NOTES.md의 성공 기준에서 가져온다. 보통은 성공 기준 충족, 위험, 복잡도나 성능, 드는 시간이다. 재 보지 않은 수치는 "추정"이라고 쓴다.
3. **추천안 하나와 이유를 쓴다.** 이유는 비교 기준에 묶는다. "더 낫다"가 아니라 "성공 기준 2(10ms 이하)를 레이아웃 변경 없이 맞춘다"처럼 쓴다. 추천안이 요청 원문이나 사용자가 앞서 정한 것과 다르면 "원문은 ~인데 ~를 추천한다"처럼 그 사실을 밝힌다.
4. **버리는 안마다 이유를 쓴다.** 안마다 한 줄씩, 구체적으로 쓴다. 어떤 조건이 바뀌면 그 안을 다시 볼지도 적으면 좋다. 이유가 사실(도구 설치 여부, 측정값, API 존재)에 기대면 어떻게 확인했는지 적는다. 예: "CMake 없음 — PATH와 Visual Studio 설치 폴더 모두 확인". 확인하지 못했으면 "미확인"이라고 쓰고, 그 사실만으로 안을 버리지 않는다.
5. **사용자가 고른다.** 되돌리기 어렵거나 성공 기준에 영향을 주는 결정은 사용자에게 묻고, 고른 안으로 진행한다. 사용자가 직접 "알아서 해"처럼 맡긴다고 말했을 때만 추천안으로 진행하고, 그렇게 했다고 알리며 결정 로그에 "정한 사람: AI(사용자가 위임)"로 쓴다. 답이 없다고 해서 사용자가 자리에 없다고 판단하지 않는다. 묻고 기다린다.

```markdown
**결정할 것:** 인벤토리 두 번째 열기 35ms → 10ms 이하 (성공 기준 2)

| 안 | 방법 | 장점 | 단점·위험 | 드는 시간(추정) |
| --- | --- | --- | --- | --- |
| A | 슬롯 위젯을 풀에서 재사용 | 레이아웃 유지, 목표 달성 예상 | 슬롯 수가 줄 때 숨김 처리 필요 | 30분 |
| B | UListView 가상화 | 1,000칸 이상에서도 빠름 | 레이아웃 재작성 | 2시간 이상 |
| C | 로딩할 때 미리 생성 | 열기 비용이 거의 없음 | 비용을 로딩과 메모리로 옮길 뿐 | 20분 |

추천: A — 성공 기준 2를 레이아웃 변경 없이 맞추고 30분 안에 끝난다.
B를 버리는 이유: 효과는 가장 크지만 레이아웃 재작성은 범위 밖이다. 1,000칸 이상 요구가 생기면 다시 본다.
C를 버리는 이유: 비용이 사라지지 않고 로딩 시간과 상주 메모리로 옮겨 간다.
어느 안으로 할까요?
```

**대안이 하나뿐일 때:** 오타 수정, 스펙이나 엔진이 방법을 정해 둔 경우처럼 합리적인 방법이 하나뿐이면 표를 만들지 않고 "대안 없음 — 이유: ..."라고 한 줄로 쓴다. 대안을 지어내지 않는다.

**작은 결정일 때:** 이름, 파일 위치처럼 되돌리기 쉬운 결정은 "A로 한다(B는 ...라서 버림)" 한 줄로 알리고 진행한다. 묻지 않는다.

**버그일 때:** 원인 가설은 systematic-debugging 방식대로 하나씩 검증한다. 원인을 찾은 뒤 고치는 방법을 이 형식으로 비교한다.

## 변경할 때마다

코드를 바꾼 직후, 다음 변경으로 넘어가기 전에 한다.

1. **두 줄 설명.** 무엇을 왜 바꿨는지, 어떤 안을 왜 버렸는지 사용자에게 두 줄로 말한다.
2. **결정 로그 기록.** NOTES.md의 `## 결정 로그`에 한 항목을 추가한다. NOTES.md가 없으면 그 절만 만든다. 쓰는 법은 아래 "결정 로그 쓰는 법"을 따른다.
3. **한 번에 쌓지 않는다.** 변경 여러 개를 한꺼번에 하고 나중에 몰아서 설명하지 않는다. 설명할 수 없는 변경이 생기면 그 부분을 먼저 이해한다. 코드를 읽고, 작은 입력으로 실행하고, 출력을 확인한다.

## 결정 로그 쓰는 법

결정 로그는 AI가 아니라 **사용자가 읽고 외워서 설명하는 글**이다. 처음부터 순서대로 읽으면 작업이 어떻게 흘러왔는지 보여야 하고, 항목 하나만 읽어도 그 결정을 몇 분 안에 설명할 수 있어야 한다.

```markdown
### D3. 인벤토리 슬롯 위젯은 다시 만들지 않고 풀에서 재사용 — T2, 14:20
- 상황: 인벤토리를 두 번째 열 때 35ms가 걸린다. 성공 기준 2는 10ms 이하다.
- 검토한 안: A 위젯 풀 재사용 / B UListView 가상화 / C 로딩할 때 미리 생성
- 고른 안과 이유: A — 레이아웃을 그대로 두고 목표를 맞춘다. 30분이면 끝난다.
- 장점: 열 때마다 하던 위젯 생성(CreateWidget 120번)이 사라진다.
- 트레이드오프: 닫아도 위젯이 메모리에 남는다(120개 상주). 슬롯 수가 줄면 남는 위젯을 숨기는 코드가 더 필요하다. 1,000칸처럼 커지면 풀만으로는 부족하다.
- 버린 안과 이유: B — 효과는 가장 크지만 레이아웃을 다시 짜야 해서 범위 밖이다. / C — 비용이 사라지지 않고 로딩 시간과 메모리로 옮겨 갈 뿐이다.
- 다른 안이 나은 경우: 칸 수가 1,000개를 넘는 요구가 생기면 B.
- 코드 위치: `InventoryWidget.cpp`의 `RefreshAll()`, `GetOrCreateSlot()`
- 복잡도·엣지 케이스: 열기당 생성 O(N) → O(새로 늘어난 칸 수) / 슬롯이 줄 때 숨김 처리 / 다루지 않음: 정렬 애니메이션
- 정한 사람: 사용자 (AI 추천 A)
- 검증: 120칸 두 번째 열기 35ms → 9ms (stat unit 3회 평균)
```

- **순서:** 번호(D1, D2…)는 결정한 순서다. 제목 끝에 작업 ID와 시각(HH:MM)을 쓴다. 시각은 명령으로 확인한다(`date +%H:%M`, PowerShell은 `Get-Date -Format HH:mm`).
- **제목:** 제목만 읽어도 무엇을 무엇으로 정했는지 알게 쓴다. 나쁜 예: "D2. 비교 방식". 좋은 예: "D2. 쿨다운 끝 판정은 허용 오차 없이 `<= 0`".
- **트레이드오프를 가장 자세히 쓴다.** 이 안을 고르면서 포기한 것, 감수한 위험, 어떤 입력이나 상황에서 이 안이 약해지는지를 쓴다. 비워 두지 않는다. 대안이 없던 결정만 "대안 없음 — 이유"로 대신한다.
- **읽기 쉽게 쓴다.** 한 줄에 한 가지만 쓰고 문장은 짧게 끊는다. 처음 나오는 용어는 괄호로 풀어 쓴다(예: "회귀 테스트(고친 버그가 다시 생기지 않는지 보는 테스트)"). "빠르다", "안전하다" 대신 수치나 예를 쓴다. 코드 이름은 백틱으로 감싼다.
- **필드를 빠뜨리지 않는다.** 위 필드를 한 줄씩 쓴다. 해당이 없으면 "복잡도·엣지 케이스" 줄만 지울 수 있다. 문단 하나로 몰아 쓰면 나중에 버린 안과 트레이드오프를 찾기 어렵다.
- **같은 결정의 새 소식은 그 항목을 고친다.** 승인, 구현 결과, 검증 결과는 원래 항목에 반영한다.
- **결정이 바뀌면 지우지 않는다.** 다른 안으로 갈아타면 원래 항목 맨 아래에 "바뀜: → D7"을 붙이고, 새 항목 D7에 "D3을 바꿈 — 이유"를 쓴다. 순서대로 읽을 때 왜 바뀌었는지 보여야 한다.
- **테스트에서 찾은 반례와 고친 버그도 항목으로 남긴다.** 무엇이 실패했는지, 원인, 고친 방법과 버린 수정안, 추가한 회귀 테스트를 쓴다.
- "정한 사람: AI"인 항목이 많다면 사용자에게 묻지 않고 넘어간 결정이 많다는 뜻이니, 다음 결정부터는 묻는다.

## 복잡도를 쓸 때

- 입력 크기를 나타내는 기호를 정의한다. 예: N = 아이템 수, M = 쿼리 수.
- 시간과 공간을 따로 쓴다.
- 해시맵처럼 평균과 최악이 다르면 둘 다 쓴다.

## AI가 만든 코드를 받아들일 때

- 생성된 diff를 읽고, 요구사항에 없는 기능이 들어왔으면 걷어낸다. 걷어낸 이유도 결정 로그에 남긴다.
- 처음 보는 API나 함수는 실제로 존재하는지, 시그니처가 맞는지 확인한다. 확인하지 못했으면 "미확인"이라고 기록한다.

## 작업을 마칠 때

1. **결정 로그를 다듬는다.** 처음부터 순서대로 읽으며 빠진 필드, 비어 있는 트레이드오프, 코드와 맞지 않는 내용(함수 이름이 바뀌었는데 예전 이름이 남은 것 등)을 고친다.
2. **완성된 코드로 질문을 만든다.** NOTES.md만 보지 말고 완성된 코드를 처음부터 다시 읽는다. 리뷰어가 이 코드를 보고 물어볼 법한 질문을 6개 안팎으로 만든다. 질문은 실제 함수와 조건에 묶는다(예: "`TryUse`에서 `<=`를 `<`로 바꾸면 무엇이 달라지나요?"). 질문마다 관련 결정 번호를 정해 두되 답과 번호는 보여 주지 않는다. **질문을 보여 주고 응답을 끝낸다.**
   - 연습 방법을 함께 안내한다: AI의 도움 없이, 복사해 붙이지 않고 직접 타이핑해서, 질문 하나에 5분 안에, 250~400자로 답한다. 실제로 설명해야 하는 자리와 같은 조건으로 연습해야 빈 곳이 드러난다.
3. **답을 대조한다.** 사용자가 답하면 질문 하나씩 NOTES.md와 코드로 대조해 맞은 점, 빠진 점, 틀린 점을 짧게 알려 준다. 사용자가 답하기 어려워한 질문은 그 결정 항목이 부족하다는 뜻이다. 그 항목의 이유와 트레이드오프를 보강한다.

질문은 다음 유형에서 고른다.

- 이 자료구조나 알고리즘을 고른 이유, 그리고 버린 대안을 골랐다면 무엇이 달라졌을지
- 이 결정의 트레이드오프: 무엇을 포기했고, 어떤 상황에서 약해지는지
- 요구사항 문서에 없던 것을 어떻게 정했는지와 그 근거
- 시간·공간 복잡도와 그 근거
- 특정 줄이나 조건을 빼거나 바꾸면 생기는 일
- 어떤 경계값과 반례를 테스트했고, 무엇을 찾아 고쳤는지
- 다루지 않은 엣지 케이스와 그 영향
- 입력이 100배 커지거나 규칙이 하나 늘면 어디를 고쳐야 하는지
- AI 제안 중 받아들이지 않은 것과 이유
- 결과가 맞다는 것을 어떻게 확인했는지, AI가 만든 결과 중 무엇을 직접 돌려 확인했는지
- 이 코드에서 가장 약한 곳은 어디이고, 거기가 깨지면 어디까지 영향이 가는지
- 실제로 쓰다가 장애나 잘못된 결과가 나오면 어디부터 확인하고 어떻게 대응할지
- 여러 곳에서 동시에 쓰거나 고치면 어떤 일이 생기는지

답하는 틀(사용자에게 함께 알려 준다)은 질문 종류에 따라 둘이다.

- 선택의 이유를 묻는 질문: 결론 한 문장 → 이유 두 가지 → 트레이드오프(포기한 것) → 다른 안과 비교 → 확인한 근거(테스트 이름, 측정값)
- 약점, 장애, 한계를 묻는 질문: 약한 지점(파일과 함수) → 파급(왜 위험하고 어디까지 번지는지) → 다음에 검증하거나 고칠 계획

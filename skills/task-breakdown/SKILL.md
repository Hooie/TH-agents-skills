# Task Breakdown

큰 문제를 작게 나누고, 하나씩 끝내고, 끝날 때마다 증거를 남긴다. 목표는 누가 봐도 "무엇을 어떤 순서로 왜 했는지"가 NOTES.md와 커밋 기록만으로 드러나게 하는 것이다.

분해, 우선순위, 작업마다의 방법은 AI가 초안을 쓰고 **사용자가 정한다.** 초안을 보여 준 뒤 사용자의 수정이나 확인을 받고 진행한다.

## 시작 조건

- NOTES.md에 목표, 성공 기준, 접근 방식이 있어야 한다. 없으면 problem-framing부터 한다.
- 작업이 한두 단계로 끝나면 이 스킬을 쓰지 않는다.

## 절차

1. **하위 문제를 나열한다.** 성공 기준을 하나씩 보며, 그 기준을 만족시키려면 풀어야 할 문제를 적는다. 문제마다 어느 성공 기준과 연결되는지 표시한다. 연결되는 기준이 없는 문제는 범위 밖 후보다.
2. **우선순위를 정한다.** 다음 순서로 정하고, 순위마다 이유를 한 줄로 적는다.
   1. 핵심 성공 기준을 직접 만족시키는 것
   2. 불확실성이 큰 것(된다고 확신할 수 없는 것). 일찍 해 봐야 계획을 고칠 수 있다.
   3. 다른 작업이 기다리는 것(선행 작업)
   4. 나머지
3. **작업으로 쪼갠다.** 한 작업은 30분 안팎, 결과가 하나이고 확인할 수 있어야 한다. "기능 전체 구현"은 작업이 아니다. "슬롯 위젯을 풀에서 재사용하고 120칸 두 번째 열기 35ms 이하 확인"이 작업이다.
4. **검증 방법을 정한다.** 자동 테스트로 확인할 수 있는 작업은 테스트 이름이나 명령을 적는다. 자동 테스트가 어려운 작업(UI 배치, 에디터 조작, 체감 확인)은 수동 확인 절차를 적고 "수동"이라고 표시한다.
5. **작업 목록을 NOTES.md에 쓴다.** 아래 표를 `## 작업 목록` 절에 넣는다.
6. **사용자 확인을 받는다.** 우선순위와 작업 목록을 보여 주고, 빼거나 바꿀 것을 묻는다. 검증이 "수동"인 작업은 테스트를 먼저 쓰지 않는다는 것(TDD 예외)도 이때 함께 확인받는다. 답을 반영하고 바뀐 이유를 결정 로그에 남긴다.
7. **한 번에 하나씩 실행한다.** 아래 실행 루프를 작업마다 돈다.
8. **막히면 다시 계획한다.** 한 작업이 예상 시간의 두 배를 넘기거나, systematic-debugging에서 수정을 3번 시도해도 해결되지 않으면 멈춘다. 더 쪼개기, 범위 줄이기, 접근 방식 바꾸기 중에서 대안을 비교해 사용자가 고르게 하고, 바꾼 계획은 표와 결정 로그에 반영한다.

## 작업 목록 형식

```markdown
## 작업 목록
| ID | 작업 | 연결된 성공 기준 | 선행 | 완료 기준 | 검증 방법 | 상태 |
| --- | --- | --- | --- | --- | --- | --- |
| T1 | 입력 파서 작성 | 기준 1 | - | 예제 3개 파싱 | `pytest tests/test_parse.py` | 완료 |
| T2 | 캐시 추가 | 기준 2 | T1 | 두 번째 호출 10ms 이하 | 벤치 스크립트 3회 평균 | 진행 중 |
| T3 | 오류 안내 문구 | 기준 3 | T1 | 잘못된 입력에 안내 표시 | 수동: 잘못된 입력 2건 실행 | 대기 |
```

상태는 `대기`, `진행 중`, `완료`, `보류(이유)` 중 하나로 쓴다. 커밋 해시는 표에 쓰지 않는다. 커밋 메시지의 작업 ID로 찾는다.

## 실행 루프 (작업마다)

1. **고른다.** 선행 작업이 끝난 것 중 우선순위가 가장 높은 작업을 고르고 상태를 `진행 중`으로 바꾼다.
2. **방법을 제안한다.** 원인을 모르는 버그를 고치는 작업이면 먼저 systematic-debugging으로 원인을 찾고, 그다음 고치는 방법을 비교한다. 구현 방법이 여러 가지인 작업이면 explain-as-you-go 형식으로 대안 2~3개를 비교하고 추천안, 고른 이유, 버린 안마다 이유를 쓴다. 방법이 하나뿐이면 "대안 없음 — 이유" 한 줄로 쓴다. 그 아래에 추천안 기준의 지시문 초안을 붙여 한 번에 보여 준다.
3. **사용자가 정한다.** 사용자가 안을 고르고 지시문을 고쳐 보내면 그 지시문대로 한다. "진행"이라고만 하면 추천안과 초안대로 한다. 사용자가 직접 고친 지시문이 대화 기록에 남도록 하는 것이 원칙이다.
4. **테스트를 먼저 쓴다.** 검증 방법이 자동 테스트면 test-driven-development 순서를 따른다: 테스트를 쓰고, 실패하는 것을 확인하고, 그다음 구현한다. 검증이 "수동"인 작업은 절차 6에서 확인받은 TDD 예외이므로 바로 구현하고, 수동 확인 결과를 남긴다.
5. **결과를 읽는다.** diff를 읽고 요청하지 않은 변경은 걷어낸다. C++ 변경이고 game-client-review가 설치되어 있으면 그 체크리스트로 본다.
6. **검증한다.** 검증 방법을 실제로 실행하고 출력을 확인한다. 실패하면 systematic-debugging으로 원인을 찾는다.
7. **기록하고 커밋한다.** 통과하면 결정 로그(explain-as-you-go), `## 검증 결과`에 한 줄, 작업 표의 상태(`완료`)를 먼저 고친 뒤, 코드와 NOTES.md를 함께 커밋한다. 커밋 메시지에 작업 ID와 검증 결과를 넣는다. 예: `T2: 인벤토리 슬롯 캐시 추가 (두 번째 열기 35ms → 9ms)`

## 지시문 형식

```text
[T2] 인벤토리 슬롯 캐시 추가
역할: 언리얼 UMG 성능을 다루는 클라이언트 개발자로서 작업해 줘.
맥락: InventoryWidget.cpp의 RefreshAll이 열 때마다 CreateWidget을 120번 호출한다. 측정값은 두 번째 열기 35ms.
고른 방법: A안(슬롯 위젯 풀 재사용). B안(UListView 가상화)은 레이아웃 재작성이 범위 밖이라 버렸고, C안(로딩 때 미리 생성)은 비용을 옮길 뿐이라 버렸다.
할 일: 슬롯 위젯을 풀에 보관하고 다시 열 때는 Setup만 호출하게 바꿔.
하지 말 것: 레이아웃 구조 변경, 다른 위젯 파일 수정, 새 플러그인 추가.
기대 결과: 바뀐 함수와 그 이유를 두 줄로 설명하고 diff를 보여 줘.
검증: 에디터 자동화 테스트 Inventory.Open을 실행하고 두 번째 열기 시간을 3회 측정해 보여 줘. 목표는 10ms 이하.
```

빠뜨리기 쉬운 것: 측정값이나 파일 위치 같은 구체적인 맥락, 고른 방법과 버린 이유, "하지 말 것", 그리고 검증 명령. 다른 에이전트나 하위 세션에 맡길 때도 같은 형식을 쓴다.

## 시간 관리 (제한 시간이 있을 때)

- 시작할 때 전체 시간과 체크포인트 시각(25%, 50%, 75%)을 NOTES.md에 적는다.
- 체크포인트마다 남은 작업과 남은 시간을 비교한다. 모자라면 우선순위가 낮은 작업을 범위 밖으로 옮기고 이유를 기록한다.
- 75% 시점부터는 새 작업을 시작하지 않는다. 남은 시간은 검증, 정리, session-handoff에 쓴다.

## 하지 않는 것

- 여러 작업을 하나의 지시로 몰아서 맡기지 않는다. "전부 만들어 줘"는 쓰지 않는다.
- 검증하지 않은 작업 위에 다음 작업을 쌓지 않는다.
- 작업 목록을 처음 한 번 쓰고 방치하지 않는다. 상태와 계획 변경을 계속 반영한다.

## 마치며

모든 작업이 `완료` 또는 이유가 적힌 `보류`가 되면 verification-before-completion으로 성공 기준을 전부 다시 확인하고 결과를 `## 검증 결과`에 적는다. 그다음 session-handoff로 마무리한다.

# Game Client Code Review

코드를 읽고 문제를 근거와 함께 보고한 뒤 반영 여부를 판단한다. 지적마다 코드 위치를 붙인다. 위치를 대지 못하는 지적은 "추정"으로 표시한다.

## 절차

1. **목적을 확인한다.** 이 코드가 무엇을 하려는지 한 문장으로 적는다. 요구사항이나 스펙이 없으면 기획에 물을 질문 목록에 올린다.
2. **아래 체크리스트를 순서대로 본다.** 해당하지 않는 항목은 건너뛴다.
3. **지적마다 재현 시나리오를 만든다.** 어떤 입력이나 상황에서 문제가 드러나는지 적는다. 가능하면 테스트 코드로 만든다.
4. **수정안을 비교한다.** 고칠 방법이 여러 가지인 지적은 2~3개를 비교하고 추천안, 고른 이유, 버린 안마다 이유를 쓴다. 형식은 explain-as-you-go의 "해결책을 제시할 때"를 따른다. 방법이 하나뿐이면 "대안 없음"이라고 쓴다.
5. **보고서를 쓰고 결론을 낸다.**

AI가 만든 C++ diff를 작업마다 확인할 때(task-breakdown 실행 루프)도 같은 체크리스트를 쓴다. 이때는 보고서 대신 지적 목록만 남겨도 된다.

## 체크리스트

### 1. 수명과 메모리
- UObject를 가리키는 멤버가 `UPROPERTY()`가 붙은 `TObjectPtr`이거나 `TWeakObjectPtr`인가? UPROPERTY 없는 원시 포인터는 GC가 추적하지 않아, 대상이 파괴되면 해제된 메모리를 가리킬 수 있다.
- 포인터를 쓰기 전에 `IsValid()`나 null 검사를 하는가? nullptr이 들어올 수 있는 인자(환경 피해의 가해자 등)는 없는가?
- 생성자에서 월드나 다른 액터에 접근하지 않는가? 생성자는 CDO를 만들 때도 실행된다. 월드 의존 초기화는 `BeginPlay`에서 한다.
- `BeginPlay`에서 등록한 타이머, 델리게이트 바인딩, 비동기 콜백을 `EndPlay`에서 해제하는가? 람다가 `this`를 캡처했다면 객체가 먼저 사라질 수 있는가?
- 일반 C++ 부분: 소유권이 분명한가(`TUniquePtr`/`std::unique_ptr`), 기반 클래스 소멸자가 virtual인가, 순회 중 컨테이너를 수정해 반복자가 무효화되지 않는가.

### 2. 정확성
- float을 `==`로 비교하지 않는가? 남은 시간이 0에 정확히 닿지 않으면 종료 조건이 영원히 거짓이 된다. `<= 0.f`나 `FMath::IsNearlyEqual`을 쓴다.
- 누적 오차를 고려했는가? 3.0에서 1/60을 180번 빼도 정확히 0이 되지 않고 10⁻¹⁵ 정도가 남는다. "정확히 끝나는 프레임" 같은 경계는 `> 0.0` 비교만으로는 한 프레임 늦어진다. 허용 오차나 정수 시간(틱, 마이크로초)을 쓰고, 실제 프레임 간격으로 누적하는 테스트로 확인한다.
- 정수 오버플로, 0으로 나누기, 음수 인덱스 가능성이 없는가?
- 같은 함수를 연속으로 호출하거나 상태가 겹칠 때(재적용, 중첩, 갱신) 동작이 정해져 있는가? 스펙에 없으면 질문 목록에 올린다.
- 프레임 시간(`DeltaTime`)에 의존하는 계산이 프레임레이트에 따라 결과가 달라지지 않는가?

### 3. 성능
- `Tick`이나 자주 불리는 함수에서 메모리 할당, 위젯·액터 생성, `LoadSynchronous`, `FindObject` 계열 검색, 문자열 조립을 하지 않는가?
- Tick이 꼭 필요한가? 타이머나 이벤트로 바꿀 수 있으면 제안한다. 필요 없는 Tick은 `PrimaryActorTick.bCanEverTick = false`.
- 비용을 말할 때는 프레임 예산(60fps 기준 약 16.7ms)과 측정값으로 말한다. 측정하지 않았으면 측정 방법(`stat unit`, Unreal Insights)을 제안한다.

### 4. 멀티플레이
- 피해, 아이템 지급, 점수처럼 게임 결과를 바꾸는 로직이 서버 권한(`HasAuthority()`)에서만 실행되는가?
- 클라이언트가 보낸 Server RPC 값을 검증하는가?
- 리플리케이트할 속성이 `GetLifetimeReplicatedProps`에 등록돼 있는가?

### 5. 스레드
- UObject를 게임 스레드가 아닌 곳에서 수정하지 않는가? 백그라운드 작업 결과는 게임 스레드로 넘겨 반영한다.
- 공유 데이터에 원자적 연산이나 락을 쓰는가? `volatile`은 동기화 수단이 아니다.

### 6. API 실재 여부
- 처음 보는 엔진 함수, 매크로, 지정자는 엔진 소스나 공식 문서로 존재 여부와 시그니처를 확인한다. AI가 그럴듯한 가짜 API를 만들어 내는 경우가 많다.
- 확인하지 못했으면 보고서에 "미확인"으로 남긴다.

### 7. 스펙 대조

코드 품질(1~6)과 따로 본다. 스펙은 요청 원문(이슈, 기획서), NOTES.md의 성공 기준과 확인 질문의 답이다. 스펙이 없으면 "스펙 없음"이라고 적고 이 항목을 건너뛴다.

- **빠졌거나 덜 된 요구:** 스펙이 요구했는데 diff에 없거나 일부만 있는 것
- **요청하지 않은 기능:** 스펙에 없는 기능, 과한 방어 코드, 범위 밖 항목. 걷어낼 것을 제안한다.
- **구현됐지만 틀려 보이는 것:** 있는 것 같지만 스펙과 다르게 동작할 것으로 보이는 것

지적마다 근거가 되는 스펙 문장을 그대로 인용한다.

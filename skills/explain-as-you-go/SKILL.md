# Explain As You Go

작업이 끝난 뒤 사용자가 AI 없이도 모든 결정을 "왜 이것인지, 왜 다른 것이 아닌지"까지 설명할 수 있게 만드는 것이 목표다. 그래서 해결책은 대안과 함께 내고, 고른 뒤에는 이유와 버린 이유를 기록한다.

## 해결책을 제시할 때

접근 방식, 설계, 자료구조와 알고리즘, 버그 수정 방법, 성능 개선 방법, 리뷰 지적의 수정안을 낼 때 모두 해당한다.

1. **대안을 2~3개 낸다.** 서로 실제로 다른 방법이어야 한다. 같은 방법의 변형은 하나로 친다. 가능하면 가장 단순한 안(지금 구조를 유지하거나 최소로 고치는 안)을 하나 넣어 비교 기준으로 삼는다.
2. **같은 기준으로 비교한다.** 기준은 NOTES.md의 성공 기준에서 가져온다. 보통은 성공 기준 충족, 위험, 복잡도나 성능, 드는 시간이다. 재 보지 않은 수치는 "추정"이라고 쓴다.
3. **추천안 하나와 이유를 쓴다.** 이유는 비교 기준에 묶는다. "더 낫다"가 아니라 "성공 기준 2(10ms 이하)를 레이아웃 변경 없이 맞춘다"처럼 쓴다.
4. **버리는 안마다 이유를 쓴다.** 안마다 한 줄씩, 구체적으로 쓴다. 어떤 조건이 바뀌면 그 안을 다시 볼지도 적으면 좋다. 이유가 사실(도구 설치 여부, 측정값, API 존재)에 기대면 어떻게 확인했는지 적는다. 예: "CMake 없음 — PATH와 Visual Studio 설치 폴더 모두 확인". 확인하지 못했으면 "미확인"이라고 쓰고, 그 사실만으로 안을 버리지 않는다.
5. **사용자가 고른다.** 되돌리기 어렵거나 성공 기준에 영향을 주는 결정은 사용자에게 묻고, 고른 안으로 진행한다. 사용자가 직접 "알아서 해"처럼 맡긴다고 말했을 때만 추천안으로 진행하고, 그렇게 했다고 알리며 결정 로그에 "정한 사람: AI(사용자가 위임)"로 쓴다. 답이 없다고 해서 사용자가 자리에 없다고 판단하지 않는다. 묻고 기다린다.

```markdown
**결정할 것:** 인벤토리 두 번째 열기 35ms → 10ms 이하 (성공 기준 2)

| 안 | 방법 | 장점 | 단점·위험 | 드는 시간(추정) |
| --- | --- | --- | --- | --- |
| A | 슬롯 위젯을 풀에서 재사용 | 레이아웃 유지, 목표 달성 예상 | 슬롯 수가 줄 때 숨김 처리 필요 | 30분 |
| B | UListView 가상화 | 1,000칸 이상에서도 빠름 | 레이아웃 재작성 | 2시간 이상 |
| C | 로딩할 때 미리 생성 | 열기 비용이 거의 없음 | 비용을 로딩과 메모리로 옮길 뿐 | 20분 |

추천: A — 성공 기준 2를 레이아웃 변경 없이 맞추고 30분 안에 끝난다.
B를 버리는 이유: 효과는 가장 크지만 레이아웃 재작성은 범위 밖이다. 1,000칸 이상 요구가 생기면 다시 본다.
C를 버리는 이유: 비용이 사라지지 않고 로딩 시간과 상주 메모리로 옮겨 간다.
어느 안으로 할까요?
```

**대안이 하나뿐일 때:** 오타 수정, 스펙이나 엔진이 방법을 정해 둔 경우처럼 합리적인 방법이 하나뿐이면 표를 만들지 않고 "대안 없음 — 이유: ..."라고 한 줄로 쓴다. 대안을 지어내지 않는다.

**작은 결정일 때:** 이름, 파일 위치처럼 되돌리기 쉬운 결정은 "A로 한다(B는 ...라서 버림)" 한 줄로 알리고 진행한다. 묻지 않는다.

**버그일 때:** 원인 가설은 systematic-debugging 방식대로 하나씩 검증한다. 원인을 찾은 뒤 고치는 방법을 이 형식으로 비교한다.

## 변경할 때마다

코드를 바꾼 직후, 다음 변경으로 넘어가기 전에 한다.

1. **두 줄 설명.** 무엇을 왜 바꿨는지, 어떤 안을 왜 버렸는지 사용자에게 두 줄로 말한다.
2. **결정 로그 기록.** NOTES.md의 `## 결정 로그`에 한 항목을 추가한다. NOTES.md가 없으면 그 절만 만든다.

```markdown
### D3. 인벤토리 슬롯 위젯 재사용
- 결정할 것: 두 번째 열기 35ms → 10ms 이하 (성공 기준 2)
- 검토한 안: A 위젯 풀 재사용 / B UListView 가상화 / C 로딩할 때 미리 생성
- 고른 안과 이유: A — 레이아웃을 유지하면서 목표를 맞추고 30분 안에 끝남
- 버린 안과 이유: B — 레이아웃 재작성이 범위 밖(1,000칸 이상 요구가 생기면 재검토) / C — 비용을 로딩과 메모리로 옮길 뿐
- 정한 사람: 사용자 (AI 추천 A)
- 변경: RefreshAll이 매번 CreateWidget 하던 것을 풀에서 꺼내 Setup만 다시 호출하도록 바꿈 (InventoryWidget.cpp)
- 복잡도: 열기당 위젯 생성 O(N) → O(신규 슬롯 수)
- 엣지 케이스: 슬롯 수가 줄어들 때 남는 위젯은 숨김 처리 / 다루지 않음: 정렬 변경 애니메이션
- 검증: 120칸 두 번째 열기 PC 35ms → 9ms (stat unit 3회 평균)
```

대안이 없던 결정은 "검토한 안: 대안 없음 — 이유"로 쓴다. 항목은 위 필드를 한 줄씩 빠짐없이 쓴다. 문단 하나로 몰아 쓰면 나중에 버린 안과 정한 사람을 찾기 어렵다. "정한 사람: AI"인 항목이 많다면 사용자에게 묻지 않고 넘어간 결정이 많다는 뜻이니, 다음 결정부터는 묻는다.

3. **한 번에 쌓지 않는다.** 변경 여러 개를 한꺼번에 하고 나중에 몰아서 설명하지 않는다. 설명할 수 없는 변경이 생기면 그 부분을 먼저 이해한다. 코드를 읽고, 작은 입력으로 실행하고, 출력을 확인한다.
4. **결정을 뒤집을 때는 지우지 않는다.** 원래 항목은 그대로 두고, 새 항목에 "D3을 뒤집음 — 이유"를 쓴다.

## 복잡도를 쓸 때

- 입력 크기를 나타내는 기호를 정의한다. 예: N = 아이템 수, M = 쿼리 수.
- 시간과 공간을 따로 쓴다.
- 해시맵처럼 평균과 최악이 다르면 둘 다 쓴다.

## AI가 만든 코드를 받아들일 때

- 생성된 diff를 읽고, 요구사항에 없는 기능이 들어왔으면 걷어낸다. 걷어낸 이유도 결정 로그에 남긴다.
- 처음 보는 API나 함수는 실제로 존재하는지, 시그니처가 맞는지 확인한다. 확인하지 못했으면 "미확인"이라고 기록한다.

## 작업을 마칠 때

NOTES.md를 다시 읽고, 사후 질의응답이나 서술형 퀴즈에서 나올 법한 질문 5개를 만들어 사용자에게 보여 준다. 답은 보여 주지 않는다. 사용자가 먼저 답하고, 그 뒤에 NOTES.md와 대조한다.

질문은 다음 유형에서 고른다.

- 이 자료구조나 알고리즘을 고른 이유와, 버린 대안을 골랐다면 무엇이 달라졌을지
- 시간·공간 복잡도와 그 근거
- 특정 줄이나 조건을 빼면 생기는 일
- 다루지 않은 엣지 케이스와 그 영향
- 입력이 100배 커지면 어디가 먼저 깨지는지
- AI 제안 중 받아들이지 않은 것과 이유
- 결과가 맞다는 것을 어떻게 확인했는지

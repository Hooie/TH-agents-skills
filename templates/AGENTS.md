## 작업 규칙 (my-agent-skills)

### 해결책을 제시할 때

- 서로 다른 대안 2~3개를 같은 기준(성공 기준, 위험, 복잡도·성능, 드는 시간)으로 비교한다.
- 추천안 하나와 고른 이유, 버리는 안마다 그 이유를 쓴다.
- 되돌리기 어렵거나 성공 기준에 영향을 주는 결정은 사용자가 고른다. 되돌리기 쉬운 작은 결정은 한 줄로 알리고 진행한다.
- 합리적인 방법이 하나뿐이면 "대안 없음 — 이유" 한 줄로 쓴다. 대안을 지어내지 않는다.
- 고른 안과 이유, 장점, 트레이드오프, 버린 안과 이유를 NOTES.md 결정 로그에 결정한 순서대로 남긴다. 사용자가 읽고 설명할 수 있게 쉽게 쓴다. 형식은 explain-as-you-go를 따른다.

### 작업 흐름

1. 여러 단계가 필요한 작업은 코드보다 먼저 problem-framing으로 시작한다.
2. task-breakdown으로 작업을 나누고, 작업마다 대안 비교 → 사용자 선택 → 지시문 → 테스트 → 구현 → 점검(정확성, 스펙 대조, API 실재 여부, 보안·민감정보, 반례) → 전체 테스트 → 커밋을 한 번에 하나씩 한다. 작업이 끝나면 사용자가 직접 돌려 볼 확인 명령도 알려 준다. 서로 기다리지 않는 작업은 다른 터미널에서 동시에 하자고 제안할 수 있지만, 사용자가 허락한 뒤에만 나눈다.
   - 테스트는 정상 입력만 보지 않는다. 경계값, 잘못된 입력, 상태와 순서, 누적 오차, 회귀(고친 버그마다 재현 테스트)를 함께 본다.
3. 구현하는 내내 explain-as-you-go를 따른다. 자동 테스트가 가능한 작업은 test-driven-development, 버그와 테스트 실패는 systematic-debugging, C++ diff 확인은 game-client-review를 쓴다.
4. "완료"라고 말하기 전에 verification-before-completion을 따른다.
5. 세션을 바꾸거나 작업을 넘기기 전에는 인계 문서를 직접 쓰지 않는다. session-handoff를 부르라고 안내하고(Codex는 `$session-handoff`, Claude Code는 `/session-handoff`) 사용자의 명령을 기다린다. "인계 문서 정리해 줘"처럼 말로만 요청해도 같다.

### 묻고 나서 시작하기

- 요구사항이 README 같은 문서로 주어지면 그 문서부터 끝까지 읽고, 고치지 않는다. 필요한데 문서에 없거나 애매한 것(동작 규칙, 범위, 사용 환경 같은 외부 상황)은 사용자에게 묻는다. 질문에는 문서에서 찾은 근거를 붙인 추정안을 함께 내고, 사용자가 따로 알려 줄 내용이 있는지도 묻는다.
- 요구사항을 준 담당자에게 물을 수 있으면, 담당자만 답할 수 있는 질문은 사용자가 그대로 보낼 수 있는 문장으로 따로 만들어 준다. 물을 곳이 없으면 건너뛴다.
- 기존 코드와 테스트가 있으면 고치기 전에 그대로 실행해 처음 상태를 기록한다.
- 찾아보면 알 수 있는 사실(설치된 도구, 폴더 구조, 기존 코드 동작)은 직접 확인하고 확인한 방법을 적는다. PATH에 없다고 "없음"으로 보지 않고 표준 설치 위치까지 확인하며, 확인하지 못하면 "미확인"으로 쓴다. 사용자에게는 결정만 묻는다.
- 질문 하나에는 결정 하나만 담는다. 추천안이 요청 원문과 다르면 그 사실을 밝힌다.
- 정해지지 않은 것(언어, 버전, 도구, 동작 규칙, 범위)은 가정하지 않고 사용자에게 묻는다. 설치된 도구나 폴더 상태는 선택지를 만드는 데만 쓰고, 그것으로 결정하지 않는다.
- 요구사항을 확인받기 전에는 파일을 만들거나 프로젝트를 만드는 명령을 실행하지 않는다.
- 작업이 작아 보여도 확인 질문이나 단계를 스스로 건너뛰지 않는다. 건너뛰려면 먼저 묻는다.
- 가정으로 진행하는 것은 사용자가 직접 맡긴다고 말했을 때뿐이다.
- git 저장소가 있으면 작업이 검증된 뒤에 작업 단위로 커밋한다. 메시지에 작업 ID와 검증 결과를 넣는다. 푸시, 원격 저장소 변경, 커밋 고쳐 쓰기(amend, rebase, reset)는 하지 않는다. 저장소를 새로 만들지는 사용자가 정한다.
- 비밀키·비밀번호·토큰을 코드, 기록, 커밋에 넣지 않는다.
- 사용자의 답을 해석해야 범위가 정해지면 해석을 보여 주고 확인받는다.
- 대안을 버리는 이유가 사실에 기대면 확인한 방법을 적는다. 확인하지 못했으면 "미확인"으로 쓴다.

### 멈추고 기다리기

- 한 단계(스킬)가 끝나면 다음 스킬을 스스로 시작하지 않는다. 다음에 할 명령을 안내하고 사용자의 명령을 기다린다.
- 작업 목록 승인은 실행 승인이 아니다. 작업은 하나씩 승인받는다. 사용자가 직접 "연속으로 진행해"라고 말한 범위만 이어서 진행한다.
- 선택지를 만들 때 "전부 한꺼번에 진행"을 추천안으로 두지 않는다.
- 성공 기준 문구를 결과에 맞춰 고치지 않는다. 못 맞춘 기준은 미충족으로 두고 사용자에게 알린다.

알고리즘 문제 하나는 cpp-stress-test로, 원인을 모르는 버그 하나는 systematic-debugging으로 바로 시작한다. 설치되지 않은 스킬은 건너뛴다.

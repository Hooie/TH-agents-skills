# Problem Framing

코드를 쓰기 전에 사용자의 요구사항을 먼저 파악한다. 무엇을 만들지, 무엇이 완료인지, 어떤 방법으로 풀지는 사용자의 답으로 정한다. **정해지지 않은 것은 가정하지 않고 묻는다.**

시작할 때 사용자에게 "problem-framing으로 시작합니다"라고 알린다.

## 작업 흐름에서의 위치

이 스킬이 첫 단계다. 순서는 problem-framing → task-breakdown → 작업마다 구현과 검증 → verification-before-completion → session-handoff이고, explain-as-you-go는 처음부터 끝까지 함께 쓴다.

사용자가 이 스킬을 직접 불렀으면 과제가 작아 보여도 아래 절차를 모두 따른다. 사용자가 부르지 않았을 때만, 다음 경우에는 이 스킬 대신 다른 길로 간다.
- 알고리즘·코딩테스트 문제 하나 → cpp-stress-test (설치되어 있지 않으면 바로 풀이)
- 원인을 모르는 버그 하나 → systematic-debugging
- 질문 하나, 한두 줄 수정 → 바로 처리

## 절대 규칙

- **가정하지 않는다.** 과제 원문에 없는 것은 정해지지 않은 것이다. 언어, 버전, 빌드 도구, 테스트 방식, 폴더 구조, 동작 규칙, 범위를 AI가 고르지 않는다.
- **답을 받기 전에는 만들지 않는다.** 사용자의 답이 오기 전에는 파일을 만들거나 고치지 않고, 프로젝트를 만드는 명령을 실행하지 않는다. NOTES.md도 답을 받은 뒤에 만든다.
- **환경은 선택지를 만드는 데만 쓴다.** 폴더 내용이나 설치된 도구를 읽어 보는 것은 괜찮다. 다만 그 결과로 결정하지 말고 "설치된 것: .NET 9, MSVC 19.44. 어느 것으로 할까요?"처럼 선택지로 보여 준다.
- **"작아서 생략"을 스스로 정하지 않는다.** 확인 질문, 접근 방식 비교, task-breakdown 중 무엇이든 건너뛰려면 사용자에게 먼저 묻는다.
- 가정으로 진행하는 경우는 사용자가 "알아서 정해", "가정하고 진행해"처럼 직접 말했을 때뿐이다. 그때도 가정마다 NOTES.md에 "가정(사용자가 위임)"이라고 적는다.

## 절차

### 1단계: 묻고 멈춘다

1. **목표를 다시 쓴다.** 과제 원문을 2~3문장으로 요약한다. 원문에 없는 내용은 넣지 않는다.
2. **정해지지 않은 것을 모두 찾는다.** 원문을 한 줄씩 읽으며, 원문만으로 답할 수 없는 것을 적는다. 다음 묶음을 빠짐없이 확인한다.
   - 환경: 언어와 버전, 빌드 도구, 테스트 방식, 폴더 구조, 실행 환경
   - 동작 규칙: 경계값(정확히 0일 때, 최댓값일 때), 같은 동작이 반복될 때, 두 기능이 동시에 걸리거나 순서가 바뀔 때(예: 보호막이 독 피해도 막는가), 잘못된 입력
   - 결과물: 무엇을 제출하는지, 무엇이 완료인지, 성능 수치 목표
   - 범위: 이번에 하지 않는 것
3. **질문을 보낸다.** 질문마다 가능한 답 2~3개와 그 답에 따라 무엇이 달라지는지 한 줄을 붙인다. 추천안이 있으면 표시하되 사용자가 고르게 한다. 질문이 많으면 중요한 순서로 번호를 매겨 한 번에 보낸다. **여기서 응답을 끝낸다.**

```text
problem-framing으로 시작합니다. 시작 전에 정해야 할 것이 5가지 있습니다.

1. 언어와 빌드 — (a) C++17 + CMake (b) C# .NET 9 / 설치된 것: MSVC 19.44, .NET 9
   → 프로젝트 구조와 테스트 방법이 달라집니다.
2. 쿨다운이 정확히 끝나는 프레임(남은 시간 0)에 바로 쓸 수 있나요? (a) 예 (b) 다음 프레임부터
   → TryUse의 비교 조건이 달라집니다.
...
```

### 2단계: 답을 받은 뒤 정리하고 멈춘다

4. **답을 기록한다.** 질문과 답을 그대로 NOTES.md에 적는다. 답이 새 질문을 만들면 1단계로 돌아가 다시 묻는다. 답을 해석해야 범위가 정해지면(예: "잘못된 입력은 0으로" → 음수만인지, NaN·무한대도 포함인지) 해석을 그대로 적용하지 말고 "이렇게 이해했는데 맞나요?"라고 확인받는다.
5. **성공 기준을 정한다.** 확인 가능한 형태로 쓴다: 통과해야 할 테스트, 수치 목표(ms, fps, 메모리, 입력 크기), 재현되지 않아야 할 증상. "잘 동작한다" 같은 기준은 쓰지 않는다.
6. **범위 밖을 적는다.** 사용자가 답한 범위를 바탕으로 이번에 하지 않을 일을 적는다.
7. **핵심 문제를 고른다.** 성공 기준에 가장 큰 영향을 주는 문제를 1순위로 정하고 이유를 한 줄로 적는다.
8. **접근 방식을 비교한다.** 1순위 문제를 푸는 방법 2~3개를 성공 기준, 위험, 드는 시간으로 비교하고 추천안, 고른 이유, 버린 안마다 이유를 적는다. 형식은 explain-as-you-go의 "해결책을 제시할 때"를 따른다. 합리적인 방법이 하나뿐이면 "대안 없음 — 이유"라고 쓴다.
9. **계획과 역할을 쓴다.** 계획은 5줄 이내로, 단계마다 확인 방법을 붙인다. AI에게 맡길 일과 사용자가 판단할 일을 나눈다.
10. **NOTES.md를 만든다.** 아래 형식으로 작업 폴더 최상단에 만든다.
11. **확인받는다.** 성공 기준, 범위 밖, 1순위 문제, 접근 방식 비교를 보여 주고, 고칠 것과 어느 접근 방식으로 갈지 묻는다. **여기서 응답을 끝낸다.**

### 3단계: 다음 단계를 안내하고 멈춘다

12. 답을 NOTES.md에 반영하고 "다음은 task-breakdown입니다(Claude Code `/task-breakdown`, Codex `$task-breakdown`)"라고 안내한다. task-breakdown을 건너뛰자고 제안할 수는 있지만, 사용자가 동의하기 전에는 건너뛰지 않는다. **여기서 응답을 끝낸다.** 다음 스킬을 스스로 시작하지 않는다.

## NOTES.md 형식

```markdown
# NOTES

## 목표
(2~3문장)

## 확인 질문과 답
- Q: ... → A: ... (사용자)

## 성공 기준
- [ ] ...

## 범위 밖
- ...

## 우선순위
1. (핵심 문제) — 이유: ...

## 접근 방식
- 검토한 안: A ... / B ... / C ...
- 고른 안과 이유: ...
- 버린 안과 이유: B — ... / C — ...
- 정한 사람: 사용자

## 계획
1. ... → 확인: ...

## 작업 목록
(task-breakdown이 채운다)

## 역할 분담
- AI: ...
- 직접: ...

## 결정 로그
(explain-as-you-go가 채운다)

## 검증 결과
(작업마다 검증한 결과와 마지막 전체 확인 결과)

## 남은 위험
- ...
```

## 게임 클라이언트 과제에서 꼭 물을 것

- 대상 플랫폼과 기준 프레임레이트. 60fps면 프레임 예산은 약 16.7ms, 30fps면 약 33.3ms다.
- 엔진과 버전. 언리얼이면 5.x 중 어느 버전인지, 블루프린트와 C++ 중 무엇으로 작업하는지.
- 싱글플레이인지 멀티플레이인지. 멀티플레이면 어떤 로직이 서버 권한인지.
- 재현 조건. 기기, 맵, 데이터 크기, 첫 실행인지 반복 실행인지.

## 하지 않는 것

- 사용자의 답을 받기 전에 구현 코드, 프로젝트 파일, NOTES.md를 만들지 않는다.
- 설치된 도구나 폴더 상태를 보고 언어나 구조를 정하지 않는다.
- 여기서 정한 성공 기준을 이후 결과에 맞춰 고쳐 쓰지 않는다. 바꿔야 하면 사용자 승인을 받고 원래 문구와 이유를 결정 로그에 남긴다.

# Session Handoff

세션이 바뀌거나 작업이 다른 사람에게 넘어가도 처음부터 다시 설명할 필요가 없게 만든다. 제출할 때는 평가자가 결과물과 과정을 한 번에 이해할 수 있게 만든다.

## 언제 쓰나

- 컨텍스트가 길어져 새 세션으로 옮기거나 compact하기 직전
- 작업을 멈추거나 다른 사람, 다른 에이전트에게 넘길 때
- 과제를 제출하기 직전
- 새 세션을 시작할 때(이때는 아래 "이어받을 때"만 한다)

## 넘겨줄 때

1. **NOTES.md를 최신으로 만든다.** 작업 목록의 상태, 결정 로그, 검증 결과가 실제 코드와 커밋에 맞는지 확인한다. 제출 직전인데 `## 검증 결과`에 성공 기준 전체를 다시 확인한 기록이 없으면 verification-before-completion부터 한다.
2. **실행 방법을 다시 확인한다.** README에 적힌 설치·실행·테스트 명령을 처음 보는 사람처럼 그대로 실행해 본다. 실패하면 README나 코드를 고친다.
3. **HANDOFF.md를 쓴다.** 아래 형식으로 작업 폴더 최상단에 만든다. 이미 있으면 덮어쓰지 말고 위쪽을 갱신한다.
4. **커밋한다.** 작업 트리를 깨끗하게 만들고 마지막 커밋 메시지에 현재 상태를 한 줄로 쓴다. 예: `handoff: T1~T4 완료, T5 진행 중(캐시 무효화 남음)`

## HANDOFF.md 형식

```markdown
# HANDOFF

## 한 줄 요약
(무엇을 만들었고 지금 어디까지 왔는지)

## 실행과 검증
- 설치: `...`
- 실행: `...`
- 테스트: `...` → 마지막 결과: 통과 12 / 실패 0 (시각)

## 끝난 일
- T1 ... (커밋 a1b2c3, `git log --oneline`에서 확인) — 검증: ...

## 남은 일 (우선순위순)
1. T5 ... — 다음에 할 첫 단계: ...

## 주요 결정
- D2 ... — 고른 안: ... / 버린 안: ... (이유는 NOTES.md 결정 로그)

## 남은 위험과 알려진 문제
- ... (재현 방법, 영향)

## 이어받는 사람에게
- 먼저 읽을 파일: NOTES.md, ...
- 건드리지 말 것: ...
```

## 제출 직전 점검

- 성공 기준마다 충족 여부와 근거(테스트 결과, 측정값, 화면)를 NOTES.md에 적었다.
- 충족하지 못한 기준은 숨기지 않고 이유와 남은 작업을 적었다.
- 성공 기준 문구가 problem-framing에서 정한 원문과 같다. 바뀌었다면 사용자 승인과 이유가 결정 로그에 있다.
- 주요 결정마다 검토한 안, 고른 이유, 버린 안과 이유가 결정 로그에 있다.
- README의 실행 방법을 방금 직접 실행해 봤다.
- `git status`가 깨끗하고, 커밋 기록만 봐도 작업 순서가 보인다.
- 사후 질의응답에 대비해 explain-as-you-go의 예상 질문에 직접 답해 봤다.

## 이어받을 때

새 세션의 첫 단계로 HANDOFF.md와 NOTES.md를 읽고, 이해한 현재 상태와 다음 작업을 3줄로 요약해 사용자에게 확인받은 뒤 시작한다. 문서와 코드가 다르면 코드를 기준으로 하고 그 차이를 기록한다.

# Problem Framing

코드를 쓰기 전에 무엇을 만들지, 무엇이 완료인지, 어떤 방법으로 풀지부터 정한다. 목표는 5분 안에 NOTES.md 한 장을 만드는 것이다. 완벽한 분석이 목표가 아니다.

시작할 때 사용자에게 "problem-framing으로 시작합니다"라고 알린다.

## 작업 흐름에서의 위치

이 스킬이 첫 단계다. 순서는 problem-framing → task-breakdown → 작업마다 구현과 검증 → verification-before-completion → session-handoff이고, explain-as-you-go는 처음부터 끝까지 함께 쓴다.

이 스킬을 쓰지 않는 경우:
- 알고리즘·코딩테스트 문제 하나 → cpp-stress-test (설치되어 있지 않으면 바로 풀이)
- 원인을 모르는 버그 하나 → systematic-debugging
- 질문 하나, 한두 줄 수정 → 바로 처리

## 절차

1. **목표를 다시 쓴다.** 과제 원문을 2~3문장으로 요약한다. 누가, 무엇을, 왜 원하는지를 담는다. 원문에 없는 내용은 넣지 않는다.
2. **확인 질문을 만든다.** 답에 따라 설계나 구현이 달라지는 질문만 3~7개 고른다. 답이 무엇이든 하는 일이 같다면 그 질문은 뺀다. 놓치기 쉬운 것은 기능끼리 만날 때다. 두 효과가 동시에 걸리거나 순서가 바뀌면 어떻게 되는지(예: 보호막이 독 피해도 막는가), 같은 동작이 반복되면 어떻게 되는지 확인한다.
   - 물어볼 상대가 있으면(출제자, 동료 역할 에이전트, 사용자) 실제로 묻고 답을 기록한다.
   - 물어볼 수 없으면 가장 그럴듯한 답을 **가정**으로 적고 진행한다. 가정마다 틀렸을 때 바뀌는 부분을 한 줄로 적는다.
3. **성공 기준을 정한다.** 확인 가능한 형태로 쓴다: 통과해야 할 테스트, 수치 목표(ms, fps, 메모리, 입력 크기), 재현되지 않아야 할 증상. "잘 동작한다" 같은 기준은 쓰지 않는다.
4. **범위 밖을 적는다.** 이번에 하지 않을 일을 2~3개 적는다. AI가 덧붙이려는 기능을 걷어낼 때 이 목록을 근거로 쓴다.
5. **핵심 문제를 고른다.** 과제에 문제가 여러 개 섞여 있으면, 성공 기준에 가장 큰 영향을 주는 문제를 1순위로 정하고 그 이유를 한 줄로 적는다. 나머지는 순위만 매긴다.
6. **접근 방식을 비교한다.** 1순위 문제를 푸는 방법 2~3개를 성공 기준, 위험, 드는 시간으로 비교하고 추천안, 고른 이유, 버린 안마다 이유를 적는다. 형식은 explain-as-you-go의 "해결책을 제시할 때"를 따른다. 합리적인 방법이 하나뿐이면 "대안 없음 — 이유"라고 쓴다.
7. **계획을 5줄 이내로 쓴다.** 고른 접근 방식을 기준으로 쓰고, 단계마다 끝났는지 확인하는 방법을 붙인다. 예: "3. 슬롯 위젯 재사용 → 120칸 두 번째 열기 35ms 이하 확인". 단계가 3개를 넘거나 제한 시간이 있는 과제라면, 이 계획을 바탕으로 task-breakdown에서 작업 목록을 만든다.
8. **역할을 나눈다.** AI에게 맡길 일(초안 작성, 반복 코드, 테스트 생성)과 직접 판단할 일(접근 방식 선택, 결과 검증, 범위 결정)을 나눈다.
9. **NOTES.md를 만든다.** 아래 형식으로 작업 폴더 최상단에 만든다. 이미 있으면 위쪽 절을 갱신한다.

## NOTES.md 형식

```markdown
# NOTES

## 목표
(2~3문장)

## 확인 질문과 답
- Q: ... → A: ... (답한 사람) / 가정: ... (틀리면 바뀌는 것: ...)

## 성공 기준
- [ ] ...

## 범위 밖
- ...

## 우선순위
1. (핵심 문제) — 이유: ...

## 접근 방식
- 검토한 안: A ... / B ... / C ...
- 고른 안과 이유: ...
- 버린 안과 이유: B — ... / C — ...

## 계획
1. ... → 확인: ...

## 작업 목록
(task-breakdown이 채운다)

## 역할 분담
- AI: ...
- 직접: ...

## 결정 로그
(explain-as-you-go가 채운다)

## 검증 결과
(작업마다 검증한 결과와 마지막 전체 확인 결과)

## 남은 위험
- ...
```

## 게임 클라이언트 과제에서 꼭 확인할 것

- 대상 플랫폼과 기준 프레임레이트. 60fps면 프레임 예산은 약 16.7ms, 30fps면 약 33.3ms다.
- 엔진과 버전. 언리얼이면 5.x 중 어느 버전인지, 블루프린트와 C++ 중 무엇으로 작업하는지 확인한다.
- 싱글플레이인지 멀티플레이인지. 멀티플레이면 어떤 로직이 서버 권한인지 확인한다.
- 재현 조건. 기기, 맵, 데이터 크기, 첫 실행인지 반복 실행인지.

## 하지 않는 것

- NOTES.md를 만들기 전에 구현 코드를 쓰지 않는다.
- 확인 질문을 핑계로 작업을 멈추지 않는다. 답이 없으면 가정을 적고 진행한다.
- 계획을 길게 쓰지 않는다. 과제가 쉬우면 계획은 3줄이면 된다.
- 여기서 정한 성공 기준은 이후 결과에 맞춰 고쳐 쓰지 않는다. 바꿔야 하면 사용자 승인을 받고 원래 문구와 이유를 결정 로그에 남긴다.

## 마치며

1. 사용자에게 목표, 가정, 성공 기준, 1순위 문제, 접근 방식 추천안을 5줄 이내로 보여 주고, 고칠 것이 있는지와 어느 접근 방식으로 갈지 한 번에 묻는다. **여기서 응답을 끝낸다.**
2. 답이 오면 NOTES.md에 반영하고, 다음 단계를 안내한 뒤 다시 멈춘다. 작업이 크면 "다음은 task-breakdown입니다(Claude Code `/task-breakdown`, Codex `$task-breakdown`)"라고 안내하고, 작으면 첫 단계를 제안한다.
3. 다음 스킬을 스스로 시작하지 않는다. 작업 목록을 만들거나 코드를 쓰는 일은 사용자가 다음 명령을 보낸 뒤에 한다.

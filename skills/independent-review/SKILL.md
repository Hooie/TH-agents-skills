# Independent Review

같은 세션이 자기 코드를 점검하면, 만들 때 놓친 것을 점검할 때도 똑같이 놓친다. 테스트를 모두 통과했는데 버그가 남는 경우가 대부분 이렇다. 그래서 검토는 대화 기록이 없는 다른 세션에게 맡긴다. 그 세션은 요구사항과 결과물만 보므로, 작업한 쪽의 생각을 따라가지 않는다.

이 스킬은 두 역할로 나뉜다.

- **요청하는 쪽(작업한 세션):** 검토 범위를 정하고, 다른 세션에 그대로 붙여 넣을 리뷰 지시문을 만들고, 돌아온 지적을 처리한다. 직접 검토하지 않는다.
- **검토하는 쪽(새 세션):** 지시문만 받아 읽기 전용으로 검토하고 지적 목록을 돌려준다.

## 요청하는 쪽의 절차

1. **범위를 정한다.**
   - 시작 커밋: 이번 작업을 시작하기 전 커밋(NOTES.md의 처음 상태나 첫 작업 커밋의 부모). 애매하면 사용자에게 묻는다.
   - 끝 커밋: 지금 HEAD. 커밋하지 않은 변경이 있으면 검토 전에 커밋할지 사용자에게 묻는다. 리뷰어는 커밋된 것만 본다.
   - `git log --oneline 시작..끝`으로 범위 안의 커밋 목록을 확인해 지시문에 넣는다.
2. **리뷰 지시문을 만든다.** 아래 "리뷰 지시문 틀"을 채운다. 넣는 것과 넣지 않는 것을 지킨다.
   - 넣는 것: 요구사항 문서의 경로, NOTES.md의 `## 성공 기준`, `## 범위 밖`, `## 확인 질문과 답`(사용자·요청자와 정한 규칙), 실행·테스트 명령, 검토 범위(커밋 두 개).
   - 넣지 않는 것: 대화 기록, `## 지금까지의 흐름`, 결정 로그의 이유와 대안 비교, "여기는 이미 확인했다" 같은 안내. 작업한 쪽의 판단이 들어가면 리뷰어가 같은 맹점을 따라간다.
3. **사용자에게 넘긴다.** 지시문을 코드 블록 하나로 보여 주고 이렇게 안내한 뒤 **멈춘다.**
   - "새 터미널에서 이 폴더로 새 세션을 열고 아래 지시문을 그대로 붙여 넣어 주세요. 리뷰 결과가 나오면 여기에 붙여 주세요."
   - 쓰는 도구가 서브에이전트를 지원하면 "제가 서브에이전트로 직접 띄울 수도 있습니다"를 선택지로 함께 묻는다. 허락받은 뒤에만 띄우고, 같은 지시문을 쓴다.
4. **지적을 처리한다.** 리뷰 결과를 받으면 explain-as-you-go "지적을 받을 때" 순서를 따른다.
   - 지적마다 내 말로 다시 쓰고, 코드와 실행으로 확인한다. 리뷰어도 틀릴 수 있다.
   - 맞는 지적: 실패하는 테스트를 먼저 추가하고 고친다(task-breakdown 실행 루프와 같은 순서, 같은 보고·커밋 형식). 동작 규칙을 정해야 하는 지적은 사용자에게 묻는다.
   - 틀렸거나 이 코드에 맞지 않는 지적: 근거(코드 위치, 실행 결과, 요구사항 문장)를 붙여 받아들이지 않은 이유를 쓴다.
   - "판단하지 않고 넘긴 것" 목록도 하나씩 본다. 다뤄야 할 것은 지적과 같이 처리하고, 아니면 `## 남은 위험`에 이유와 함께 옮긴다.
5. **기록한다.** NOTES.md `## 검증 결과`에 한 단락으로 남긴다: 언제, 어떤 범위를, 어떤 방식(새 터미널 / 서브에이전트)으로 검토했는지, 지적 몇 개 중 몇 개를 고쳤고 몇 개를 어떤 이유로 받아들이지 않았는지. 고친 지적은 결정 로그에 항목으로 남긴다.

## 리뷰 지시문 틀

````markdown
너는 이 저장소의 변경을 처음 보는 코드 리뷰어다. 아래 정보만으로 검토한다. 이 변경을 만든 대화나 이유는 모른다고 생각하고, 결과물만 보고 판단한다.

## 무엇을 만들었나
(한두 문장. 무엇을 바꿨는지만 쓰고 왜 그렇게 했는지는 쓰지 않는다)

## 요구사항
- 요구사항 문서: (경로)
- 성공 기준: (NOTES.md `## 성공 기준`을 그대로 붙인다)
- 정해진 규칙: (NOTES.md `## 확인 질문과 답`에서 동작 규칙만 붙인다)
- 범위 밖: (NOTES.md `## 범위 밖`)

## 검토 범위
- 시작 커밋: (해시) / 끝 커밋: (해시)
- 볼 명령: `git log --oneline 시작..끝`, `git diff --stat 시작..끝`, `git diff 시작..끝`
- 실행·테스트 명령: (명령)

## 규칙
- 읽기 전용이다. 파일을 고치거나 만들지 않는다. git 상태를 바꾸는 명령(add, commit, checkout, reset, stash 등)을 쓰지 않는다. 테스트와 실행 명령은 돌려도 된다.
- 다른 에이전트나 서브에이전트를 띄우지 않는다. 혼자 검토한다.
- 요구사항 문서는 방향을 적은 문서이고 모든 상황을 나열하지 않는다. 문서가 말하지 않는 동작은 이 기능을 쓰는 사람이 당연히 기대할 동작을 기준으로 판단한다. 문서에 없다는 것은 아무렇게나 동작해도 된다는 허락이 아니다.
- 특히 본다: 성공 기준마다 그것을 실제로 확인하는 테스트가 있는지, 경계값, 상태를 기억하는 코드에서 같은 흐름을 반복하거나 가리키던 대상이 사라졌을 때, 요구사항에 근거가 없는 방어 코드·추상화(과잉 설계), 문서의 실행 방법대로 실행되는지.
- 지적마다 직접 확인한다. 확인하지 못한 지적은 "미확인"이라고 쓴다.

## 돌려줄 형식
1. 결론: "그대로 마쳐도 됨" 또는 "꼭 고칠 것 있음"
2. 지적 목록: 지적마다
   - 심각도: 꼭 고칠 것 / 고치면 좋은 것
   - 위치: 파일과 줄(또는 함수)
   - 내용: 무엇이 문제인지 한두 문장
   - 근거: 재현 방법이나 실행한 명령과 결과, 또는 요구사항 문장
3. 판단하지 않고 넘긴 것: 검토하다가 범위 밖이라고 보고 넘긴 동작을 한 줄씩, 이유와 함께. 넘긴 것이 없으면 "없음".
4. 확인한 명령: 검토 중 실행한 명령 목록
````

## 하지 않는 것

- 요청하는 쪽이 리뷰를 직접 하거나, 리뷰어의 결론을 미리 짐작해 지시문에 넣지 않는다.
- 리뷰 결과를 확인 없이 그대로 고치지 않는다. 결론이 "그대로 마쳐도 됨"이어도 "판단하지 않고 넘긴 것" 목록은 본다.
- 사용자 허락 없이 서브에이전트나 새 세션을 띄우지 않는다.
- 커밋되지 않은 변경을 리뷰 범위에 넣는다고 가정하지 않는다.

(이 스킬은 obra/superpowers의 requesting-code-review(MIT)에서 "대화 기록 없이 만든 리뷰 지시문"과 "판단하지 않고 넘긴 것 목록" 아이디어를 참고해 새로 썼다.)
